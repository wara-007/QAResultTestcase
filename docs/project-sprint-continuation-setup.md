# นำ Project ไปทำต่อใน Sprint โดยคงประวัติเดิม

## ติดตั้ง

สำรองฐานข้อมูลก่อน แล้วรันไฟล์นี้ใน Supabase SQL Editor ของโปรเจคที่แอปใช้งาน:

`supabase/migrations/20261017185922_project_sprint_continuation.sql`

ต้องติดตั้ง migrations เดิมจนถึง `20261002121258_project_defect_register_totals.sql` ก่อน รวม personal_test_performance, result_origins และ project_history
ไฟล์ใหม่รันซ้ำได้ ไม่สร้าง Project หรือรูปซ้ำ และไม่เปลี่ยนการอนุมัติของ PO

ตรวจสอบด้วยบัญชีที่เข้าสู่ระบบ:

```sql
select public.project_sprint_continuation_ready();
```

ผลต้องเป็น `true` (ฟังก์ชันนี้ไม่เปิดให้ anonymous เรียก)
โค้ดใหม่จะปฏิเสธการเปลี่ยน Sprint จนกว่าจะติดตั้ง schema แต่ยังแก้ชื่อ/รายละเอียดใน Sprint เดิมได้
หลังรัน SQL ให้นำโค้ดเวอร์ชันนี้ขึ้นระบบด้วย — การแก้ในเครื่องไม่ใช่ deployment

## พฤติกรรม

- จัดการ Project → เลือก Sprint ปลายทาง → ใส่เหตุผล → บันทึก
- Sprint เดิมยังเห็น Project ในรายการหลัก พร้อมป้ายส่งต่อ; กดชื่อเปิดข้อมูลย้อนหลังแบบอ่านอย่างเดียว
- Sprint ใหม่ใช้งาน Project ID เดิม พร้อมป้ายต่อจาก Sprint ก่อน
- มีตัวกรอง ทั้งหมด / ทำอยู่ใน Sprint นี้ / ส่งต่อแล้ว, ค้นหา, QA และแบ่งหน้า
- ยอด Sprint รวมสถานะปัจจุบันและสถานะ ณ วันที่ส่งต่อ; งานที่ต้องติดตามนับเฉพาะงานปัจจุบัน
- รายงานบุคคลใช้ข้อมูลย้อนหลังที่ตรึงไว้และต้นกำเนิด Result ไม่มอบเครดิตให้ผู้ส่งต่อ
- การบันทึก Test Case + Result ใช้ RPC เดียวเพื่อป้องกันการส่งต่อคั่นกลางระหว่างบันทึก
- รูปและวิดีโออ้างอิงไฟล์เดิม ไม่ทำสำเนา การส่งต่อไม่เรียก Google Sheets หรือ upload รูปใหม่
- ระบบปัจจุบันลบ Result เป็นการลบ reference ไม่ลบไฟล์จริง จึงยังคงรูปที่ประวัติอ้างอิงไว้
- การลบ Project จริงรวบรวมหลักฐานทั้งปัจจุบัน/ประวัติ แล้วใช้ cleanup เดิม; ไม่ลบ Google Sheets ต้นฉบับ

## ข้อมูลเก่า

การส่งต่อก่อนติดตั้งมีเพียงยอดสรุป แสดงป้าย “ข้อมูลย้อนหลังแบบสรุป” ไม่มี Results เก่า/QA/Approval เก่าที่ไม่ได้บันทึกไว้
ระบบไม่ใช้ข้อมูลปัจจุบันปลอมเป็นรายละเอียดในอดีต วันเข้าและผู้ดำเนินการที่ไม่ทราบจะไม่ถูกแต่งขึ้น

## ตรวจรับหลังติดตั้ง

1. เลือก Project ทดสอบที่นำเข้าครบ ส่งต่อ 67 → 68 แล้วตรวจรายการหลักทั้งสอง Sprint
2. เปิดประวัติ 67 เปลี่ยน Result/QA/ชื่อ Project ใน 68 กลับมา refresh ประวัติ 67 ต้องเหมือนเดิม
3. ตรวจ Results/Highlights/ภาพ/วิดีโอ, ลิงก์งานปัจจุบัน, ค้นหา/แบ่งหน้า
4. ส่งต่อ 68 → 67 → 69 ต้องมีหนึ่งแถวต่อ Project ต่อ Sprint และเปิดช่วงประวัติเดิมได้ด้วย URL
5. Viewer ต้องอ่านได้ตามสิทธิ์ แต่ส่งต่อหรือแก้ snapshots ไม่ได้; สลับ ID ไป Project อื่นต้องถูกปฏิเสธ
6. Import ที่ยังมี queued/loading/error ต้องส่งต่อไม่ได้; โหลดครบแม้ complete flag ค้างต้องส่งต่อได้
7. ตรวจ Approval เดิมไม่ถูก reset และผลงานต้นกำเนิดไม่ย้ายตาม Project

## ข้อจำกัดการตรวจสอบ

ชุดทดสอบในเครื่องใช้ PostgreSQL ผ่าน PGlite สำหรับ transaction, rollback และ RLS แต่ไม่ได้พิสูจน์ concurrency แบบหลาย session ของ PostgreSQL จริง
ควรตรวจหลายคนบันทึก Result พร้อมส่งต่อบน staging ก่อน production; การล็อกใช้ Project row เป็นจุดร่วม และไม่มีการส่งต่อเมื่อ import ยังไม่ครบ
ตรวจ browser ของ Dashboard/list ปัจจุบันแล้ว ส่วนการทดสอบส่งต่อ/หน้าย้อนหลังกับ schema จริงต้องทำหลังผู้ดูแลติดตั้ง SQL; งานนี้ไม่ได้รัน SQL ระยะไกลหรือ deploy ให้
ถ้าไฟล์ภายนอกถูกเจ้าของลบหรือถอนสิทธิ์ ระบบไม่สามารถคืนไบนารีเดิมจาก reference ได้

## Rollback

อย่าลบตาราง snapshot เพื่อย้อนโค้ด เพราะเป็นประวัติจริง ให้เก็บ schema และข้อมูลไว้ก่อน
หากต้องย้อน deployment ให้หยุดการเปลี่ยน Sprint ชั่วคราว ไม่ควรกลับไปใช้ flow เดิมที่ย้ายแล้วไม่สร้างรายละเอียดประวัติ

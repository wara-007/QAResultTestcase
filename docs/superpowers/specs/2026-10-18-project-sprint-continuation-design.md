# Project continuation across Sprints

วันที่: 2026-10-18
สถานะ: รอผู้ใช้ตรวจสเปกก่อนจัดทำแผน implementation

## เป้าหมายที่ตกลง

เปลี่ยนจากการย้าย Project ออกจาก Sprint เดิม เป็นการนำ Project เดียวไปทำต่อใน Sprint ใหม่
Sprint เดิมต้องยังเห็น Project ในรายการหลัก เปิดดูข้อมูลในขณะส่งต่อได้ และรายงานย้อนหลังไม่เปลี่ยนตามงานใหม่
ไม่มีการสร้าง Project, Test case, Google Sheet หรือไฟล์หลักฐานซ้ำ

## ข้อเท็จจริงของระบบปัจจุบัน

- `projects.sprint_id` ระบุ Sprint ปัจจุบันเพียงหนึ่งแห่ง
- `private.record_project_history` บันทึกการเปลี่ยน Sprint พร้อม `moveSnapshot` ซึ่งเป็นยอดสรุป ไม่ใช่รายละเอียดทั้ง Project
- `buildSprintDashboard` นับเฉพาะ Project ปัจจุบัน และแยก Project ที่ส่งต่อออกไว้ใน `movedOut`
- หน้า Sprint Projects กรองด้วย Sprint ปัจจุบัน จึงไม่แสดง Project เดิมหลังส่งต่อ
- มี `result_origins` และข้อมูลรายบุคคลสำหรับแยกต้นกำเนิดผลงานแล้ว ต้องรักษาความหมายเดิม
- การเข้าดู Project/หลักฐานใช้สิทธิ์จากระบบเดิม ไม่ใช่สิทธิ์ที่ได้จาก URL

## แนวทางที่เลือกและขอบเขต

ใช้ Project เดียว พร้อมบันทึกแต่ละช่วงที่ Project อยู่ใน Sprint และ snapshot แบบอ่านอย่างเดียว
ไม่เลือกการคัดลอก Project เพราะจะทำให้ Results, Sheets และ Approval แยกเป็นคนละชุด
ไม่แสดงข้อมูลสดแทนข้อมูลย้อนหลัง เพราะจะทำให้รายงาน Sprint เก่าเปลี่ยนเมื่อมีการแก้ไขภายหลัง

สิ่งที่เปลี่ยน: การส่งต่อ, รายการ Projects ทั้งสองหน้า, Dashboard, หน้าย้อนหลัง, รายงานบุคคล และการเก็บรักษาข้อมูลย้อนหลัง
สิ่งที่ไม่เปลี่ยน: ขอบเขตสิทธิ์, Google OAuth, รูปแบบนำเข้า/ซิงค์ Sheets, การตัดสิน Approval, สูตรสถานะของ Test case
ไม่มีการซิงค์ Google หรือย้าย/ลบไฟล์ภายนอกเพียงเพราะส่งต่อ Sprint

## แบบข้อมูลและความรับผิดชอบ

1. `projects.sprint_id` ยังเป็น Sprint ที่กำลังทำงานปัจจุบัน เพื่อให้เส้นทางและโค้ดเดิมทำงานต่อได้
2. เพิ่มข้อมูลการเข้าร่วม Sprint เป็นรายช่วงเวลา (`project_sprint_participations`): Project, Sprint, เวลาเข้า/ออก, ผู้ส่งต่อ, เหตุผล, ช่วงก่อนหน้าและถัดไป
3. หนึ่ง Project มีช่วงที่เปิดอยู่ได้เพียงหนึ่งช่วง การตรวจนี้บังคับที่ฐานข้อมูล
4. เพิ่ม snapshot header และ snapshot cases ที่ผูกกับช่วงเวลา โดยมี schema version, Project metadata, ยอดสรุป, QA/การมอบหมาย, Approval ณ เวลานั้น, Cover, รายการแท็บ/การ map และ Test cases พร้อม Steps/Results/Defects/Highlights
5. รายละเอียด snapshot แยกจาก header เพื่อให้โหลด Dashboard เฉพาะยอดสรุปและแบ่งหน้ารายละเอียดได้ ไม่ดึง API/log ทั้งหมดขึ้นหน้า Sprint
6. หลักฐานเก็บเป็น reference ไปไฟล์เดิม ไม่คัดลอกไบนารี และไม่เก็บ OAuth token/credential ใน snapshot
7. snapshot และข้อมูลต้นทางที่ถูกอ้างอิงเป็น immutable สำหรับผู้ใช้ทั่วไป ไม่อนุญาตให้แก้ผ่าน client โดยตรง
8. สถิติ snapshot ใช้ตัวนับที่ตรวจสอบแล้วตัวเดียวกับหน้า Project รวมกฎไม่นับ Cover/แถวที่ไม่ใช่ Test case และ deduplicate Defects

## ขั้นตอนส่งต่อ

1. ผู้มีสิทธิ์จัดการเลือก “นำไปทำต่อใน Sprint” พร้อม Sprint ปลายทางและเหตุผลที่จำเป็น
2. ส่ง Project version ที่เปิดอยู่เพื่อ optimistic concurrency; ตรวจว่า Sprint ปลายทางอยู่กลุ่มเดิมและไม่ใช่ Sprint ปัจจุบัน
3. ธุรกรรมฐานข้อมูลล็อก Project แล้วเก็บ snapshot ของข้อมูลที่บันทึกแล้ว ปิดช่วงเดิม เปิดช่วงใหม่ และอัปเดต Sprint ปัจจุบันพร้อม audit history
4. snapshot กับการส่งต่อต้องสำเร็จหรือยกเลิกพร้อมกัน ถ้ามี import/write ที่ยังไม่เสร็จ ต้องรอหรือแจ้งให้ทำให้เสร็จก่อน ไม่สร้างภาพย้อนหลังที่มีข้อมูลครึ่งชุด
5. หลังส่งต่อ refresh รายการทั้งสอง Sprint และข้อมูล Project โดยไม่สร้าง ID ของ Project ใหม่
6. คำขอที่ส่งซ้ำหรือแข่งกันต้องไม่สร้างสองช่วงที่เปิดอยู่ ไม่บันทึก snapshot ซ้ำ และไม่เขียนทับ version ที่เปลี่ยนแล้ว

## หน้าจอและเส้นทาง

### Sprint เดิม

- Project ยังอยู่ในตารางหลัก พร้อมป้าย “ทำต่อใน Sprint 68” และวันส่งต่อ
- ชื่อ Project เปิดหน้าย้อนหลัง ไม่เปิดข้อมูลปัจจุบันโดยไม่บอก
- คอลัมน์ความคืบหน้า/Defects/QA/Approval ของแถวย้อนหลังแสดง snapshot ณ ตอนส่งต่อ
- มีลิงก์แยก “เปิดงานปัจจุบัน” และลิงก์ Sprint ปลายทาง
- ไม่แสดงซ้ำในตารางหลักและกล่อง “Projects ที่ย้ายออก”; กล่องเดิมถูกรวมเข้ารายการหลัก

### Sprint ใหม่

- แสดง Project ในรายการหลักพร้อมป้าย “ต่อจาก Sprint 67”
- เปิด workspace เดิมที่แก้ไขได้ตามสิทธิ์ ผล/หลักฐานเก่ามีอยู่ตามเดิม
- แสดงผล “ยกมาจาก Sprint ก่อน” แยกจาก “ทำใน Sprint นี้” โดยใช้ต้นกำเนิด Results และ baseline ที่บันทึกตอนเข้า ไม่ใช้ชื่อผู้ส่งต่อเป็นผู้ทดสอบ

### การค้นหาและการกลับเข้ามา Sprint เดิม

- ตัวกรองรายการมี ทั้งหมด / ทำอยู่ใน Sprint นี้ / ส่งต่อแล้ว; ค่าเริ่มต้นทั้งหมด
- ค้นหา/กรอง QA และ pagination ครอบคลุมทั้งแถวปัจจุบันและแถวย้อนหลัง
- หาก Project กลับเข้า Sprint เดิม ให้ตารางแสดง Project เดียว ใช้ช่วงปัจจุบันก่อน และมีประวัติให้เปิดช่วงเก่าที่ตรึงไว้ได้
- หากไม่ได้อยู่ Sprint นั้นแล้ว ใช้ snapshot ตอนออกครั้งล่าสุดเป็นแถวสรุป โดยไม่รวมยอดจากทุกช่วงซ้ำกัน

### หน้าย้อนหลัง

- มี URL ตามกลุ่ม/ปี/Sprint/Project/ช่วงเวลา และ refresh แล้วอยู่ข้อมูลช่วงเดิม
- แสดงป้ายอ่านอย่างเดียว เวลาเก็บข้อมูล ผู้ส่งต่อ เหตุผล และ Sprint ปลายทางชัดเจน
- ดู Test cases, Steps, Results, Highlights, ภาพ/วิดีโอ, Defects และข้อมูล Approval ที่บันทึก ณ เวลานั้น
- ใช้ส่วนแสดงผล Preview เดิม แต่ไม่มีปุ่มแก้ไข ซิงค์ ส่ง Approval หรือจับคู่ Step
- โหลดจาก snapshot ที่บันทึกไว้เท่านั้น ไม่เรียก Sheets สดมาเติมรายละเอียดที่ขาด
- ลิงก์ “เปิดงานปัจจุบัน” จึงจะออกจากบริบทข้อมูลย้อนหลัง

## กติกาการนับ

- ตารางและยอดสรุป Sprint รวม Project ปัจจุบันด้วยข้อมูลสดที่บันทึกในระบบ และ Project ที่ส่งต่อด้วยยอด snapshot
- แสดงจำนวนแยก “กำลังทำใน Sprint” / “ส่งต่อแล้ว” ควบคู่ยอดรวม เพื่อไม่สื่อว่าทุก Project ยังทำอยู่ใน Sprint นี้
- ยอดสถานะ Test cases คือสถานะ Project ณ ขอบเขตเวลาของแถวนั้น ไม่ใช่จำนวนเคสที่ผู้ใช้ทำใหม่ใน Sprint นี้
- ผลงานรายบุคคลและกิจกรรมใช้ Sprint ต้นกำเนิดของ Result ไม่โอนผลงานเดิมไปให้ Sprint ใหม่
- สำหรับข้อมูลนำเข้า/ข้อมูลเก่าที่ไม่ทราบต้นกำเนิด แสดงเป็นข้อมูลยกมา/ไม่ทราบต้นกำเนิด ไม่อนุมานเป็นผลงานใหม่
- ประวัติบุคคลใช้ข้อมูล snapshot สำหรับช่วงที่ปิดแล้ว เพื่อไม่ให้การลบ/แก้ Results ในปัจจุบันเปลี่ยนผลงานเก่า
- หน้ารวมหลาย Sprint ต้องนับ Project แบบ distinct และแยกยอดรายช่วง ไม่บวก snapshot ซ้ำเป็นจำนวน Project จริง
- งานที่ต้องติดตามแยก “งานปัจจุบัน” กับ “สถานะตอนส่งต่อ” ไม่เอา Defect จาก snapshot เก่าไปแจ้งเป็นงานเปิดปัจจุบันซ้ำ
- Approval เดิมไม่ถูกรีเซ็ตเมื่อส่งต่อ; ประวัติแสดงสถานะ ณ ตอนส่งต่อ ส่วนงานปัจจุบันแสดงสถานะจริงปัจจุบัน

## ข้อมูลเก่าและการ rollout

- สร้างช่วงปัจจุบันให้ Project เดิมโดยไม่แต่งวัน/ผู้สร้างที่ไม่ทราบ
- นำ move history เดิมมาสร้างรายการย้อนหลังตามข้อมูลที่ยืนยันได้ ใช้ยอดสรุปเดิมและป้าย “ข้อมูลย้อนหลังแบบสรุป”
- ไม่สร้าง snapshot รายละเอียดปลอมจาก Results ปัจจุบัน หากไม่มีรายละเอียดในประวัติเดิม ให้บอกว่าไม่มีข้อมูลส่วนนี้
- การส่งต่อหลังติดตั้งจึงรับประกัน snapshot รายละเอียดครบตามข้อมูลที่บันทึกในระบบ
- migration ต้อง rerun ได้โดยไม่สร้างช่วง/ประวัติซ้ำ รักษา Project IDs, Results, Approval และ Google Sheet IDs เดิม
- เตรียม SQL migration และคำแนะนำให้ผู้ใช้รันเอง ตามแนวทางของโปรเจคนี้ ไม่รัน SQL ระยะไกล ไม่ deploy/push โดยอัตโนมัติ
- โค้ดตรวจว่ามี schema ใหม่ก่อนให้ส่งต่อ หากยังไม่ติดตั้งให้แจ้งชัดเจน ไม่ส่งต่อด้วย flow เดิมที่สร้าง snapshot ไม่ครบ

## สิทธิ์ การรักษาหลักฐาน และความล้มเหลว

- การอ่าน snapshot/หลักฐานต้องผ่านสิทธิ์ดู Project เดิม พร้อมตรวจ Project–Sprint–ช่วงเวลาให้ตรงกันทุกครั้ง
- การส่งต่อยังใช้สิทธิ์จัดการ Project เดิม ไม่เพิ่มสิทธิ์จากการเป็นเจ้าของ URL หรือจาก client metadata
- ลบ Result/เปลี่ยนไฟล์ต้นฉบับในงานปัจจุบันได้ แต่ห้ามลบไฟล์ที่ snapshot ยังอ้างอิงอยู่; cleanup ลบได้เมื่อไม่มี reference จากงานปัจจุบันหรือ snapshot
- การลบ Project จริงตามสิทธิ์เดิมจึงลบช่วงเวลา/snapshot/Approval และ cleanup หลักฐานของ Project ทั้งหมด ไม่ลบ Google Sheets ต้นฉบับ
- หากไฟล์ภายนอกถูกเจ้าของลบ/เพิกถอนสิทธิ์ภายหลัง ให้แจ้งหลักฐานไม่พร้อม ไม่แสดงรูปอื่นหรือข้อมูลใหม่แทน
- หาก snapshot อ่านไม่ได้ ให้แสดงข้อผิดพลาดพร้อม retry ไม่ fallback ไปข้อมูลปัจจุบันอย่างเงียบ ๆ

## Acceptance checks

1. ส่งต่อ 67 → 68 แล้วเห็น Project ID เดิมในรายการหลักทั้งสอง Sprint และไม่ซ้ำในหน้าเดียวกัน
2. แก้/ลบ Result, Defect, QA, ชื่อ Project หรือ Approval ใน 68 แล้ว snapshot 67 ไม่เปลี่ยน
3. เปิด URL ย้อนหลังโดยตรง/refresh ยังคงบริบท Sprint และช่วงเดิม ไม่มีคำสั่งแก้ไข
4. 67 → 68 → 69 และ 67 → 68 → 67 มีประวัติครบ ไม่บวกยอดช่วงเดียวกันซ้ำ
5. ยอดบน Dashboard ตรงกับแถวปัจจุบัน + snapshot ที่เลือก และกฎกรอง Test cases/Defects เดิม
6. Results เก่ายังคงเครดิตเดิม Results ใหม่อยู่ Sprint ใหม่ ไม่มีเครดิตให้ผู้นำเข้า/ผู้ส่งต่อแทนผู้ทดสอบ
7. ชื่อ/รูปแบบคอลัมน์จาก Sheets, Highlights, รูป/วิดีโอ และผลร่วมหลาย Test cases ยังดูได้โดยไม่อ่าน Sheets ซ้ำ
8. ส่งต่อซ้ำ/สองคนส่งต่อพร้อมกัน/ส่งต่อขณะ import ไม่ทำให้เกิด snapshot หรือช่วงเปิดซ้ำ/ข้อมูลครึ่งชุด
9. Viewer ส่งต่อไม่ได้ การแก้ URL เพื่อเปิด snapshot หรือหลักฐานของ Project ที่ไม่มีสิทธิ์ถูกปฏิเสธ
10. ประวัติเก่าบอกข้อจำกัดจริง migration รันซ้ำได้ และการติดตั้ง schema ไม่ครบไม่ทำให้ย้ายแบบเดิมต่อโดยไม่เตือน
11. หลังลบ Result ปัจจุบัน รูปที่ snapshot อ้างอิงยังดูได้; ลบ Project จริง cleanup ครบและ Google Sheets ยังอยู่
12. รัน unit/integration tests, typecheck, lint, production build และตรวจ flow ในเบราว์เซอร์ก่อนยืนยันว่าเสร็จ
